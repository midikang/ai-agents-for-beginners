What Are AI Agents?

Understanding the building blocks that make AI systems act autonomously in the real world

Imagine you're booking a vacation...

You tell an app: "Find me a warm beach destination for next week." Within seconds, it checks flight prices, compares hotel availability, reads reviews, books your tickets, and sends you a confirmation email.

You didn't click through 20 websites. You didn't manually check calendars. You just asked — and it acted.

That's what an AI Agent does. It doesn't just generate text. It takes actions.

What makes something an AI Agent?

AI Agents are systems that enable Large Language Models (LLMs) to perform actions by giving them access to tools and knowledge.

🌍
Environment

The defined space where the agent operates — like a travel booking system, a database, or a web browser

📡
Sensors

How the agent gathers information from its environment — API responses, database queries, file contents

⚙️
Actuators

How the agent changes the environment — booking a room, sending an email, updating a database

🧠
The LLM Brain

The reasoning engine that interprets information and decides which actions to take

The key difference: AI Agents ACT

Outside of agent systems, LLMs are limited to generating content based on your prompt. They can explain how to book a flight, but they can't actually book one.

Inside agent systems, LLMs can accomplish tasks by using tools available in their environment — like calling a booking API, running code, or searching the web.

💡
Key Insight

The difference between an LLM and an AI Agent is like the difference between a smart friend who gives advice and a personal assistant who actually does the work for you.

Types of AI Agents

Not all agents are created equal. Here are the main types you'll encounter when building agentic systems:

⚡

Simple Reflex

Acts on predefined rules — like an email filter that auto-forwards complaints to customer service.

🎯

Goal-Based

Creates plans to achieve goals — like figuring out the best route from your house to the airport (car → train → flight).

⚖️

Utility-Based

Weighs tradeoffs to maximize value — balancing convenience vs. cost when booking travel.

📚

Learning Agents

Improves over time using feedback — like adjusting future bookings based on post-trip surveys.

🏢

Hierarchical

Multiple agents in tiers — a manager agent breaks tasks into subtasks for worker agents to complete.

🤝

Multi-Agent

Agents work together cooperatively or competitively — one books flights, another books hotels.

When should you use AI Agents?

Not every problem needs an agent. Here's when agents shine:

1
Open-Ended Problems

Tasks where the steps can't be hardcoded — the LLM needs to figure out what to do dynamically.

2
Multi-Step Processes

Tasks requiring complexity — using tools and information over multiple turns, not just one-shot retrieval.

3
Improvement Over Time

Tasks where the agent can learn from feedback (from the environment or users) to provide better results.

Your First AI Agent in Action

Tracing what happens when you ask an agent to recommend a vacation destination

You type: "Find me a warm beach destination"

Before we dive into building complex agents, let's trace what actually happens under the hood when you run a simple travel agent. This will ground everything in something concrete — you'll see the exact journey your request takes through the system.

We'll use the Microsoft Agent Framework (MAF) — Microsoft's framework for building agents with Azure AI Foundry.

Step 1: Creating the agent

First, we define what the agent knows how to do. In this case, we give it a tool — a Python function that returns a list of destinations.

CODE 
@tool(approval_mode="never_require")
def get_destinations() -> list[str]:
    """Get a list of popular vacation destinations."""
    return [
        "Barcelona", "Paris", "Tokyo",
        "Bali", "Sydney"
    ]

The @tool decorator

That @tool line is magic — it tells MAF "this function is now a tool the agent can call." The framework automatically converts your function into a function schema the LLM can understand.

Agent Design Patterns

Common architectural approaches for building agents that solve real-world problems

Patterns help you build faster

You've seen a basic agent. But what happens when tasks get more complex? Instead of reinventing the wheel, developers use proven design patterns — blueprints for structuring agent behavior.

These patterns emerged from real production systems. They're not academic theory — they're battle-tested approaches that solve specific problems you'll encounter when building agents.

The main patterns you'll use

🔧

Tool Use

Giving agents access to external capabilities — APIs, databases, code execution. The foundation of all agentic systems.

🔄

Agentic RAG

Agents that decide when and how to retrieve information from knowledge bases — instead of blindly retrieving every time.

📋

Planning

Breaking complex goals into subtasks — like a project manager decomposing "book a vacation" into flights + hotel + car rental.

🤝

Multi-Agent

Multiple specialized agents working together — one agent books flights, another books hotels, they coordinate to complete the trip.

🧠

Metacognition

Agents that reflect on their own reasoning — like a writer who reviews their draft and decides if it needs more work.

When to use which pattern

Choosing the right pattern depends on your problem. Here's a decision tree based on real use cases:

?
Does the agent need to access external data or APIs?

→ Use Tool Use. This is the foundation — almost all agents use tools.

?
Does it need to search through large amounts of documents?

→ Use Agentic RAG. The agent decides which documents to retrieve and when.

?
Is the task multi-step and requires sequential decision-making?

→ Use Planning. The agent creates a plan and executes it step-by-step.

?
Can the task be divided among specialized experts?

→ Use Multi-Agent. Each agent handles what it's best at.

?
Does the agent need to evaluate its own output quality?

→ Use Metacognition. The agent reviews and refines its work.

Patterns often combine

In production systems, you rarely use just one pattern. A complex agent might use Tool Use to access data, Planning to break down tasks, and Multi-Agent to divide work among specialists.

💡
Start Simple, Add Complexity

Don't start with multi-agent systems. Build a single-agent system with Tool Use first. Only add Planning or Multi-Agent when you have a concrete reason — like tasks that require multiple sequential steps, or specialized expertise that's hard to fit in one agent.

Tool Use — Giving Agents Superpowers

How agents go from chatbots to systems that actually DO things

Tools are where the magic happens

You've seen an agent call a simple get_destinations function. But tools can be so much more — they're how agents interact with the real world.

A tool can be anything: a database query, an API call, a code interpreter, a web search. Agents without tools are just chatbots. Agents with tools can book flights, analyze data, send emails, and automate workflows.

What kinds of tools can agents use?

🗄️

Database Queries

Fetch data from SQL databases, NoSQL stores, or data warehouses — like retrieving customer orders or sales data.

🌐

External APIs

Call third-party services — weather APIs, stock prices, payment gateways, CRM systems, or booking platforms.

💻

Code Execution

Run Python code in a sandbox to perform calculations, generate charts, or process data — like a data analyst.

🔍

Web Search

Search the web for up-to-date information — like using Bing or Google to find current news or product reviews.

📄

File Operations

Read, write, and search files — PDFs, CSVs, images, or text documents stored locally or in the cloud.

✉️

Communication

Send emails, Slack messages, or SMS notifications — like confirming a booking or alerting a team.

How tool calling works

When you give an agent a tool, the framework does three things automatically:

1
Generate a schema

The framework reads your function and creates a schema — a description of what the tool does and what parameters it needs.

2
Send schema to LLM

The framework sends the schema (along with the user's message) to the LLM. The LLM decides whether to call the tool.

3
Execute and return result

If the LLM calls the tool, the framework executes it, gets the result, and sends it back to the LLM for a final response.

💡
The Framework Saves You Time

Without a framework like MAF, you'd have to manually parse the LLM's response, figure out which function it wants to call, extract the parameters, run the function, and send the result back. MAF does all of that for you automatically.

Real example: Weather tool

Let's build a tool that gets the current weather for a city. Here's how you'd define it:

CODE 
@tool
def get_weather(city: str) -> str:
    """Get the current weather for a city."""
    # In production, call a real weather API
    return f"The weather in {city} is sunny, 72°F."

When you attach this tool to an agent and ask "What's the weather in Tokyo?", the agent will:

  1. See the user's message
  2. Check its available tools and see get_weather
  3. Call get_weather("Tokyo")
  4. Get back "The weather in Tokyo is sunny, 72°F"
  5. Reply to the user: "It's sunny and 72°F in Tokyo!"

Security: Making tools safe

Giving an agent access to tools is powerful — but it comes with risks. What if the agent accidentally deletes data? Or leaks sensitive information?

🔒
Read-only by default

Start with read-only tools (database SELECTs, not UPDATEs). Only add write permissions when absolutely necessary.

🔒
Require approval for destructive actions

Use approval_mode="always_require" for tools that modify data — the agent will ask the user before executing.

🔒
Run in sandboxed environments

Execute code in isolated sandboxes (like Azure AI's Code Interpreter) so malicious code can't harm your system.

Multi-Agent Systems — Teamwork Makes the Dream Work

When one agent isn't enough: dividing complex tasks among specialized experts

Why use multiple agents?

Imagine booking a vacation with one person handling flights, hotels, car rentals, activities, and travel insurance. They'd be overwhelmed.

Now imagine a team where one person specializes in flights, another in hotels, another in activities. Each expert handles what they're best at. That's multi-agent systems.

When to use multi-agent vs. single agent

⚠️
Start Simple

Don't jump to multi-agent systems immediately. Start with a single agent. Only split into multiple agents when you hit concrete problems — like one agent getting confused trying to do too many different things, or tasks that naturally divide into specialized roles.

Use multiple agents when:

📊
Tasks require diverse expertise

Like healthcare — one agent for diagnostics, one for treatment plans, one for patient monitoring. Each has specialized knowledge.

⚡
Large workloads need parallelization

Processing 1000 customer support tickets — divide them among multiple agents working simultaneously.

🎯
One agent keeps choosing the wrong tool

If a single agent with 20 tools keeps calling the wrong ones, split it into specialized agents with 3-5 tools each.

Multi-agent patterns

🔄

Sequential Handoff

Agent A finishes, then hands the task to Agent B — like an assembly line. Example: Research agent → Writer agent → Editor agent.

💬

Group Chat

Multiple agents discuss and collaborate on a single task — like a team brainstorming session. One might suggest ideas, another critiques, another refines.

🏢

Hierarchical

A manager agent breaks tasks into subtasks and assigns them to worker agents — like a project manager delegating to a team.

🤝

Collaborative Filtering

Multiple expert agents contribute to a recommendation — like asking 3 stock analysts (fundamental, technical, industry) for their input before deciding.

Example: Refund processing system

Let's design a multi-agent system for handling customer refunds. Instead of one overwhelmed agent, we use specialists:

👤
Customer Agent

Handles customer communication — asks for order details, explains the refund process

🔍
Validation Agent

Checks if the refund request is valid — order exists, within refund window, not already processed

💳
Payment Agent

Processes the actual refund through the payment gateway — handles retries if the transaction fails

⚖️
Compliance Agent

Ensures the refund follows company policies and regulations — flags suspicious patterns

✅
Resolution Agent

Confirms completion, sends confirmation email, updates customer support ticket status

Each agent has a clear role. They work together sequentially — the customer agent hands off to validation, which hands off to payment, and so on.

The tradeoff: Complexity vs. Specialization

💡
More Agents = More Coordination Overhead

Every agent you add increases complexity. You need to handle communication between agents, manage failures (what if one agent crashes?), and debug interactions. Only use multi-agent when the benefits (specialization, parallelization) outweigh the coordination cost.

Think of it like a company: a startup with 3 people can move fast because there's minimal coordination overhead. A 100-person company needs managers, processes, and meetings to coordinate. Same with agents.

Building Production-Ready Agents with Microsoft Agent Framework

Everything you need to deploy reliable, observable, and scalable AI agents

From prototype to production

You've built agents. You've seen them work in notebooks. But deploying to production is different — you need monitoring, error handling, security, and scalability.

That's where Microsoft Agent Framework (MAF) shines. It's designed for enterprise production systems, not just demos.

What makes MAF production-ready?

📊

Observability

Built-in OpenTelemetry integration — every tool call, reasoning step, and error is traced. You can see exactly what went wrong.

🔒

Security

Role-based access control, private data handling, content safety filters — all managed through Azure AI Foundry.

💾

Durability

Agents can pause, resume, and recover from errors. Long-running workflows won't lose progress if a server restarts.

🎛️

Control

Human-in-the-loop workflows — agents ask for approval before executing critical actions.

⚡

Multi-Agent Orchestration

Built-in patterns for sequential, concurrent, group chat, and hierarchical agent coordination.

🌐

Cloud-Agnostic

Run agents in containers, on-prem, or across multiple clouds — not locked into Azure.

Key MAF concepts

🧵
Threads

Threads store conversation history across turns — serialize them to a database to resume conversations days later.

🔀
Workflows

Pre-defined multi-step processes where agents are components — like a flowchart with conditional branches and parallel execution.

🔌
Middleware

Hooks that run before/after tool calls or LLM requests — useful for logging, authentication, or rate limiting.

🧠
Memory Providers

Plug in external memory services like Mem0 to give agents long-term memory of user preferences.
